## 2026-09-19 · 正文公式排版还原 + 新增「内容自洽性」检查（补掉一个真实盲区）

**改动人**：阿酉（质检方）

**起因**：主人验收成品时发现 ——「它里面的公式使用的字符并非我们常用的，
学习中绝不会是这种复杂的」。典型例子：`T = 2pi sqrt(L/g)`、
`x = A cos(omega t + phi)`。

### 现象与根因

成品**公式框**里的式子是对的（走 MathML），问题出在**正文散文**：
作者写作时顺手敲了机器写法。全库扫下来 **174 处字段、313 个片段**。

拆开是两类，第二类更要紧：

1. **显示问题** —— 正文里的公式从来没做过排版。`build_site.py` 的 `paras()`
   只做 HTML 转义，不做任何公式处理。
2. **一致性问题** —— 正文公式**不参与任何校验**。校验器只比每条公式的
   `expr` 字段，正文写什么它一概不看。于是 osc-06 出现了
   「定义正文写 `v = lambda f`，符号表却把波长定义成 `wavelength`」——
   同一个物理量在一张卡片里两个名字，**六道检查一道都没抓到**。

### 改了哪些文件

| 文件 | 改动 |
|---|---|
| `work/prose_math.py` | **新增**。把正文里的机器写法还原成教材写法（`2pi sqrt(L/g)`→`2π √(L/g)`、`F_合`→`F<sub>合</sub>`、`A^2`→`A²`）。纯查表 + 正则，不含物理判断，幂等。自带 21 条自测。 |
| `work/build_site.py` | 正文渲染由 `E()`（纯转义）改为 `prose()`，覆盖定义 / 物理意义 / 推导 / 例题 / 常见错误 / 符号表 / 校验记录。**公式框的 `expr` 一个字符都没动。** |
| `work/qc.py` | 新增第七项检查「内容自洽性」；并修掉保留字 `lambda` 无法求值的缺陷（见下） |
| `work/kb/06_oscillation_wave.json` | `wavelength` → `lambda`（20 处），与 osc-05 统一，页面显示为 λ |

### 为什么必须改

- **显示**：学习者看到的是 `2pi sqrt(L/g)`，教材上从来不这么写。
- **一致性**：正文公式不进校验 = 一个没人看的角落。这次是命名不一致，
  下次可能是正文里的公式抄错系数 —— 同样没人抓。

### 修 qc.py 的保留字缺陷（关键）

把 osc-06 的符号统一成 `lambda` 之后，独立复算立刻报 **3 处 `invalid syntax`**。

根因：`physkit/expr.py` 的 `GREEK` 词表里明确写着 `"lambda": "λ"`
（生产解析器是自己写的，能处理）；而 `qc.py` 的独立复算**刻意**改用
Python 原生 `ast`，`lambda` 是 Python 保留字，**在语法层就被拒绝**，
连环境都轮不到查。

这不是内容的错，是**质检工具自己的缺陷**：独立复算器无法校验含合法符号
`lambda` 的公式，等于把这类公式整批漏掉。而且它表现为「独立复算失败」，
看多了会被当成噪音忽略掉 —— 那比不报更危险。

修法：求值前把保留字换成安全名（`lambda` → `_lam_`），取名字时再还原。
**只改名字，不动任何计算逻辑**，独立复算「两条代码路径互不相同」的原则不变。

修完：独立复算回到 **145 项全部相符**。

### 新增检查：内容自洽性（qc.py 第七项）

规则：**正文里用到的量，本卡片的符号表里应该能找到。**

- 符号名拿英文单词充数（如 `wavelength`）→ **硬问题，拦**；
- 正文引用了本卡片没定义的量（推导时顺手用到邻近知识点的 θ、ω）→
  **软提示，不拦**，列出来给人判断。

当前结果：**0 硬 / 4 软**。4 条软提示分别是 ene-03 的 θ、cir-03 的 a_c、
osc-03 的 θ 与 ω —— 都是推导时引用了相邻知识点的量，不影响正确性。

### 对已有内容的影响

- **对正确性零影响**：`expr` 字段一个字符没动；符号表只改了 06 章那一个名字。
- 成品体积 441.4 KB → 444.7 KB（多出来的是 `<sub>` 标签），远低于 2 MB 防呆上限。
- 493 项内容校验、145 项独立复算，改动后**仍然全过**。

### 验证

- `python work/build_site.py` → 493 / 493 通过
- `python work/qc.py --check` → 指纹 0 / 覆盖门槛 0 / 独立复算 0（145 项）/
  成品一致性 0 / 质量扫描 0 / 内容自洽性 0 硬 4 软 → ✔ 通过
- 正文残留扫描：机器写法从 98 处降到 **1 处**，且那 1 处是符号表 MathML
  里的变量名，不是正文

### 基线

改动后已重冻：`work/qc.py` → `6f5ec5f3a27be5d0`（其余冻结文件未变）

## 2026-09-19 · 网络体检：探测顺序对齐到「真正干活的那条通道」

**改动人**：阿酉（质检方）　**授权来源**：主人选定「先补内容（电磁学等）」，
开跑第 7~21 批之前的开跑前加固

### 改了哪个文件、哪一行

| 文件 | 位置 | 改动 |
|---|---|---|
| `work/net_guard.py` | `CANDIDATE_PORTS` | `[10808, 10809, 1080, 7890, 7897]` → `[7897, 10808, 10809, 1080, 7890]`；仅**提升 7897 到首位**，其余相对顺序不变 |

### 为什么必须改

这是「体检通道 ≠ 干活通道」的洞，**靠一次巧合活着**。

- **体检**走 `net_guard.evaluate()`，它按 `CANDIDATE_PORTS` 顺序试，
  老顺序下 **10808（v2rayN）排第一**；
- **干活**走 `orchestrator.py` 的 `CONFIG["代理"] = http://127.0.0.1:7897`（SakuraCat）。

两条通道**互不知情**。于是 SakuraCat 一掉而 v2rayN 还活着时：
体检探 10808 → 通 → 报「网络正常」→ 编排器放心派活 →
**Codex 走 7897 连不上 chatgpt.com** → 一轮轮空转 → 连续失败 4 轮 → 停机。

实测（2026-09-19 07:32）两个端口**碰巧都活着**，且 `evaluate()` 确实挑了 10808，
`7897` 与 `10808` 各自直连 chatgpt.com 均返回 `200 Connection established` ——
洞因此从未暴露。但 7897 是主人桌面上常开的客户端提供的，
**随时可能退出**；后面还有 15 批要无人值守地连跑，不能把成功率押在巧合上。

### 为什么选「改顺序」而不是「加自动切换」

另一条路是让编排器按体检结果**动态改写**代理端口（SakuraCat 掉就切 v2rayN）。
**故意不选**：按实测，v2rayN(10808) 的建连失败率是 15%（20 次请求失败 3 次，
含两次 20 秒 TLS 握手死等），SakuraCat(7897) 是 0%。Codex 靠 WebSocket 长连接，
切到一条 15% 失败率的通道上，**"能连上"只是把显性失败换成隐性断续** ——
2026-09-18 夜里连停 5 轮零产出正是这么来的。

所以取**「宁可等，不要静默降级」**：体检如实反映干活通道，
不通就报不通，编排器去等网络恢复（本来就是设计好的自愈路径），
不烧额度、也不把内容生产押在一条烂线路上。

### 对已有内容的影响

- **对正确性零影响**：不碰任何内容、任何校验逻辑。
  变的只是「体检先看哪个端口」，是一个**探测顺序**。
- 覆盖面还扩大了：改前只探到 10808 也算通，改后 10808/10809/1080/7890
  仍全在候选里，只是**优先级降后**。任一通道活着都还能被探到，
  只是需要「干活通道优先」时才先探 7897。
- 与 `CONFIG["代理"]` 的一致性：现在两者默认同为 7897。
  ⚠ **耦合提醒**：日后若 `orchestrator.py` 里换了代理端口，
  `CANDIDATE_PORTS` 首位要跟着换（两处已在各自注释里写了互指提醒）。

## 2026-09-19 · 编排器：把「额度用尽」从生产失败里摘出来（资源故障 ≠ 内容失败）

**改动人**：阿酉（质检方）　**授权来源**：主人指出「实际上是 gpt 用量的问题，
它的用量 5 小时重置一次」（2026-09-19 11:29）

### 现象与真因

07:33 开跑后第 7~16 批一路顺产（10 批 / 92 分钟）。**09:19:49 起骤停**，
之后每 30 分钟醒一次、每次撞同一堵墙，连续失败累到 7 停机。

读 `logs/轮次_NNN_codex输出.txt` 的**报错原文**（不能只看症状 ——
「额度用尽」「服务端满载」「被掐死」三者的表面症状几乎相同：

```
{"type":"error","message":"You’ve hit your usage limit. Upgrade to Pro … try again at 11:44 AM."}
{"type":"turn.failed","error":{"message":"…try again at 11:44 AM."}}
```

报错原文**自己就写着几点重置**（11:44），与主人说的完全一致。

### 为什么必须改（不是"看着烦"，是它会把新章节锁死）

编排器原来把额度用尽一律当成「Codex 没正常收工」的生产失败，于是连锁出三件事：

1. **伪造对账冲突** —— 仍拿**上一轮的** `work/交接单.json` 去跟本轮起始时间比，
   条条判「虚报」，还附一条「交付文件本轮没被改动 —— 这一批实际上没产出」。
   Codex 压根没参与，却被判"对账没过"。
2. **下一轮被写成硬禁令** —— `build_prompt()` 把这类实打实的冲突翻译成
   **「先处理这个：上一轮没对上账 …… 这一轮不要开新章节」** →
   **新章节永远开不了工**，循环原地打转。
3. **计入「连续失败」→ 停机** —— 看着像"项目坏了"，其实只是要等窗口重置；
   而且每次都要人手动去洗状态。

> 这一条和 07:33 修的那次是**同一个坑的第二种触发方式**：
> 上次是「没活可干」，这次是「额度用完」，都会经 `上轮对账问题` → `build_prompt()`
> 把新章节锁死。上次只清了状态（治标），这次改成机制（治本）。

### 改了哪些文件、哪几处

只动 `work/orchestrator.py` 一个文件，四处（互相关联，缺一不可）：

| # | 位置 | 改动 |
|---|---|---|
| 1 | 新增 `QUOTA_KEYS` / `detect_quota(hb, human_file)` | 从事件流的 `last_err` **和**人读流水两处认「usage limit」，顺带用正则抠出「几点重置」 |
| 2 | `run_codex()` 收尾处 | 把额度判定**放在「退出码 != 0」之前** —— 额度问题的现象正好是「退出码 1 + 0 分钟」，先走下面那条就会被写成生产失败 |

## 2026-09-19 · 【已知限制 · 未修】数值比较的「1.0 下限」会让小量级内容失效

**发现人**：阿酉（代产第 21 章时实测撞上）
**状态**：⚠ **本次只记录 + 给出规避办法，故意不改代码**（理由见末尾）

### 现象

核物理的量级在 10⁻¹¹ ~ 10⁻³⁰。把第 21 章按真实量级写出来之后，`validate.py` 报：

```
✘ [不等式关系] 情境「一次裂变」：m_before - m_after = 3e-28，0 = 0，不满足 m_before - m_after > 0
★ 以下错误声称会被抓住、实测却抓不住：  （3 条）
```

`3e-28 > 0` 被判成"相等"。

### 根因（`work/physkit/checks.py` 三处）

| 行 | 代码 | 后果 |
|---|---|---|
| 243 / 265 | `tol = spec.get("tol", 1e-6)`；`if abs(got-ref) <= tol * max(1.0, abs(ref))` | `max(1.0, …)` 让 |ref| < 1 时的容差**固定为 1e-6 绝对** |
| 371 / 404 | `tol = spec.get("tol", 1e-6)`；`if abs(a-b) <= tol * max(1.0, abs(a))` | 同上（跨公式一致） |
| 478 / 505 / 507 | `tol = spec.get("tol", 1e-9)`；`scale = max(abs(a), abs(b), 1.0)` | 同上（不等式关系） |
| `kb.py` 166 | `if abs(a - b) > 1e-6 * scale:` ← **硬编码** | **`trap_test` 不受 `tol` 控制** |

**一句话**：`max(1.0, |值|)` 这个下限，等于给所有小于 1 的量发了一张「免费容差」。
量级低于 1e-6 时，数值检查实际上在比"两个都约等于 0 的数"——
**看着通过，其实没在比**。这比不报更危险。

### 规避办法（已实测有效，**不需要改校验器**）

1. **把场景参数写成宏观量级** —— 首选。核反应按 **1 mol** 计：
   单核 2.7×10⁻¹¹ J → 1 mol 1.62×10¹³ J；单核质量亏损 3×10⁻²⁸ kg → 1 mol 1.8×10⁻⁴ kg。
   全部落在 1e-4 ~ 1e13，默认容差够用，`trap_test` 也能正常抓住。
2. **确实没法放大的量级**（核半径 10⁻¹⁵ m、光子能量 10⁻¹⁹ J）：
   在对应 `numeric` / `consistency` / `compare` 检查项里**显式加 `"tol"`**
   （如 `"tol": 1e-20`）—— 这三个检查都认 `spec.get("tol", …)`。
   ⚠ 但 `trap_test` **不认**，所以这类量级的常见错误请标 `caught_by: "人工审核"`。

> 上述办法已写进 `work/批次计划.md` 第 20 批的注意事项，
> 让执行方不必再踩一遍（**这是代产之外更值钱的部分**）。

### 为什么这次不改代码

把下限从 `1.0` 拿掉、改成相对容差，**在原理上更正确**；但风险是：
现有 1321 项检查里有相当一部分 `ref` 是**按三位有效数字写的**
（它们今天能通过，正是因为 1e-6 那个宽松的绝对容差兜住了取整误差）。
一旦改成严格相对容差，这些**作者写对的检查会集体报红**——
**为了让新内容好写，去动已经验收通过的 1321 项检查，是本末倒置。**

### 后续建议（留给将来）

若日后要真正修，应当：
1. 先写一个**实验性脚本**，对现有全部数值检查**同时用两套容差各算一遍**，
   统计"改成相对容差后会红掉多少项"；
2. 若为 0，再改；若不为 0，**必须逐条核对那些 ref 是否只是取整**，
   确认是取整不精确就补精度，不能一律放松或一律收紧；
3. 改完重冻基线并登记。

**在此之前，按上面的「规避办法」走，不要绕开这条限制去凑数字。**

### 1. 下标规则重写：贪婪字符类 → 定长记号 + 全量词表

旧规则的下标部分是贪婪字符类，只要作者漏写乘号或空格，

## 2026-09-29 晚 第六批：公式框括号 / ½ 分数 / 平排名下标（显示层）

主人看线上页面反馈三件事：① 重力做功印成 `W_G = mgh1 − h2`，"h1h2 外面没有括号"；
② 弹力做功 `0.5kx1² − x2²` 同样没括号；③ 动能 `Ek = 0.5mv²`，"0.5 不常用，
常用的是二分之一"。本批**仍然只动显示层**（`prose_math.py`），不动 `physkit`、
不动任何 `expr` 与校验器。

### 1. 根因：physkit 的 MathML 不输出围栏括号

查证：源数据全对（`m*g*(h1 - h2)`、`0.5*k*(x1^2 - x2^2)`），但 physkit 生成的
MathML 里「和/差因子」只是裸 `<mrow>`，浏览器平铺渲染，括号"隐形"——
mg(h₁−h₂) 变成 mgh₁−h₂，**公式含义被改变**，是显示层 bug 里最严重的一类。

修法：`display_mathml` 新增**树状修补**（ElementTree 解析 → 结构规则 → 序列化）：

- **围栏**：mrow 直接子层含 `+/−` 且与左右邻居靠乘号相连（乘号是挂 tail 上的
  裸文本节点 `·`/`⁢`，不是 `<mo>`）→ 补 `<mo>(</mo>…<mo>)</mo>`；
  靠 `+ − =` 相连的位置不补（`W_总 = Ek2 − Ek1` 教材不加）。
- **乘点清理**：`k·(…)` → `k(…)`、`(…)·v` → `(…)v`，教材乘法靠紧排。
- **0.5 → ½**：`<mn>0.5</mn> → <mfrac><mn>1</mn><mn>2</mn></mfrac>`，
  全库公式框共 8 条（动能/弹性势能/弹力做功/面积速度/振动能量/自感储能/
  初中动能/初中机械能），全部是系数，无误伤。

### 2. 平排「字母+数字」名拆下标

- MathML：`h1/x1/m1/T0` 等 38 种单字母+数字名（普查确认全是"同一物理量的
  第几个/初末态"）→ h₁ 式下标；`Ek/Ep/Ek1/Ek2/Ep1/Ep2` 六种 E 系 → E_k2 式。
  `(?<!<msub>)` 防止在 msub 底数位置拆出嵌套双层下标（Ep_s 的底不动）。
- 正文（prose）：同一类平排名 → h₁/T₁/E_k2。字母集白名单
  `E F I R T U V W / d f h l p q s t u v x` + 单个数字。
  **刻意排除 m 系**：初中压强章正文里 m2 大多是"平方米"（0.02 m2、
  1 m2=10 000 cm2），转了就是制造错误；MathML 里的 m1/m2 全是质量，照转。
  已核查正文无「数字+字母+数字」jammed 形态（唯一一处 2T3 也是真下标）。
- 正文 `0.5*` → ½：只认「0.5 后紧跟乘号」的系数形态；
  `0.5 × 3`（算式）、`0.5 m/s`（测量值）不动。

## 2026-10-05 容差护栏：容差不得大到把答案整个吞掉（改冻结文件，需重冻）

**改动人**：阿酉（质检方）
**授权来源**：主人原话 ——「第三个那什么我看不懂啊，反正按效果好的去处理就行了」（2026-10-04 对冻结机制类问题的总体授权）

### 问题

`physkit/checks.py` 两处判据都是 `tol * max(1, |ref|)`。
当被检量本身小于 1 时，`max` 取 1，等于给了 `tol` 的绝对容差（默认 1e-6）。
**被检量比 tol 还小的时候，容差比答案还大**：

| 实例 | 参考值 | 默认 tol | 实际容差 | 后果 |
|---|---|---|---|---|
| particle-04 由代表原子尺度反推原子核尺度 | 1e-6 m | 1e-6 | 1e-6 | 把结果改成 0（差 1e-6）仍判「相符」 |

执行方在 2026-10-04 用「给源显式补 tol」堵住了绝大多数微小量，
但这是逐条补漏，默认机制本身的洞还在，新写的卡仍会踩。

### 为什么没有照执行方的建议改成 rtol / atol 分离

先做了影子评估（脚本：`_qc_tol_sim.py`，不改任何冻结文件）：

- 纯相对判据 `tol*|ref|` → **11 条既有检查转失败**，其中 osc-03 单摆频率是源参考值只写了 6 位有效数字、cir-08 / ac-03 / mdl-09 / mdl-38 是理论零的浮点残差，都是真数据而非错误。
- 相对 + 1e-12 绝对底线 → 3 条转失败，且**反而更松**：固定 1e-12 底线会盖掉已显式收紧到 6.4e-19 的源 tol，微小量「改成 0」的拒绝率从 49/50 掉到 39/50。
- 相对 + tol×1e-6 底线 → 8 条转失败。

即：**改默认判据收益 1 条、代价 3~11 条误伤，还会引入新漏洞。不划算。**

### 实际改动

只新增一个 `_tolerance(ref, tol)`，两处判据改用它：

```
limit = tol * max(1.0, abs(ref))
if ref != 0:
    limit = min(limit, 0.5 * abs(ref))   # 容差不得超过参考值的一半
```

- `ref == 0`（理论零：完全失重视重、对称位置合场强等）没有「比例」可谈，仍走原绝对容差。
- 正常量级下 `tol*|ref|` 远小于 `0.5*|ref|`，本函数**不起任何作用**，不会误伤。

### 改动一：理论零走「离 0 够不够近」，不套比例护栏

| 文件 | 位置 | 改动 |
|---|---|---|
| `physkit/checks.py` | 新增 `_zero_limit(spec, tol)` | 理论零用的绝对容差：源给了 atol 就用 atol，否则退回 tol |
| `physkit/checks.py` | `check_numeric` | 检查项声明 `expected_zero` 时，判据改为「两端各自距 0 ≤ 绝对容差」 |
| `physkit/checks.py` | `check_consistency` | 同上，判据改为「两条路径各自距 0 ≤ 绝对容差」 |

语义：「理论零」不是「算出来恰好是 0」，而是物理上真值就是 0（临界张力、逃逸临界总机械能、
半周期正弦电压、竖直最高点竖直分速度）。这类结果必然是 1e-15 级残差，**没有「参考值的比例」可谈**，
只能问离 0 够不够近。

**影响面只有 5 条**（全库显式声明 `expected_zero` 的检查项：cir-08、ac-03、mdl-09×2、mdl-38），
其余检查项判据一字未动，`particle-04` 那条老漏洞的防护原样保留。

### 改动二：扫描一次都没算出数值时判失败

| 文件 | 位置 | 改动 |
|---|---|---|
| `physkit/checks.py` | `check_scan` | 原 `if v is None: continue` 改为计入 bad；全部点都没算出数值时明确判失败 |

原逻辑：某点算不出数值就悄悄跳过，若所有点都算不出，`bad` 为空 → 反而判「通过」，
等于一次都没验证却发了合格证（执行方报的 kine-06 曾 61 个点全部无值仍通过）。
现源已由执行方修好，本次改的是机制。
